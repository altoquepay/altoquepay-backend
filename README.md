# altoquepay-backend

REST API of **AlToquePay**, a web application for neighborhood corner stores (*bodegas*) to manage the credit they grant to their customers. It is built with FastAPI and consumed by the Angular web frontend, [altoquepay-frontend](https://github.com/altoquepay/altoquepay-frontend).

> **Status:** early development (`0.x`). The shared kernel, the ACL facade contracts, the `regulation` context (BCRP caps), the `iam` context (sign-in and passwords), the `stores` context (store registration, profile and administration), the `customers` context (customer accounts and their credit conditions), the `catalog` context (products and their images), the `credit` context (purchases, weekly French schedules and installments), the `billing` context (cycles, statements, payments and late interest) and the `reporting` context (customer portal, dashboard and period report) are done.

## Tech stack

- Python 3.13 or newer
- FastAPI, served by Uvicorn, with Pydantic for validation
- PostgreSQL 16 with SQLAlchemy 2.0 (async) and asyncpg
- Alembic for database migrations
- JWT authentication (PyJWT)
- OpenAPI documentation with Swagger UI, generated by FastAPI
- pytest, pytest-asyncio and HTTPX for tests
- Ruff for linting and formatting

## Getting started

### Requirements

- Python 3.13 or newer
- Docker with Docker Compose

### Run in development

Create and activate a virtual environment:

```bash
python -m venv .venv
source .venv/bin/activate
```

On fish, activate it with `source .venv/bin/activate.fish`; on Windows, with `.venv\Scripts\activate`.

Install the dependencies:

```bash
pip install -r requirements.txt
```

Create your local configuration and set your own `JWT_SECRET` (generate one with `openssl rand -hex 32`):

```bash
cp .env.example .env
```

Start the database, apply the migrations and start the development server:

```bash
docker compose up -d
alembic upgrade head
fastapi dev app/main.py
```

The API starts on `http://localhost:8000` and reloads on file changes. The Swagger UI is available at `http://localhost:8000/docs`.

Sign-in and password reset requests share 20 attempts per IP every 15 minutes, and each email gets at most 3 reset links in that time. The counts live in the database, so every worker and instance of the API shares them.

The limit per IP needs each client's real IP:

- With nothing in front of Uvicorn, it already sees it.
- With the compose in `deploy`, it is already set to Caddy's address.
- Behind Nginx on the same machine, the default `FORWARDED_ALLOW_IPS` (`127.0.0.1`) works, as long as Nginx sends `X-Forwarded-For $proxy_add_x_forwarded_for`.
- Behind an AWS Application Load Balancer, set `FORWARDED_ALLOW_IPS` to the VPC CIDR.

Never set it to `*`. Uvicorn would then take the first address in `X-Forwarded-For`, which the client writes, so anyone could dodge the limit by sending a different one on each request.

### Tests and linting

The integration tests need the database running. They create and migrate their own `<database>_test` database, so they never touch the data you use for manual checks.

```bash
pytest
ruff check .
ruff format .
```

### Deploy

The `deploy` folder runs the backend on one Linux server with Docker Compose:

- Caddy gets the HTTPS certificate and forwards requests to the API.
- PostgreSQL stays on the internal network.
- The API applies the migrations every time it starts.

The team's server is an Amazon Lightsail instance with Ubuntu 24.04 on the 2 GB plan. It has a static IP and ports 22, 80 and 443 open. A free [DuckDNS](https://www.duckdns.org/) name points to that IP.

Every release deploys itself. Pushing a tag such as `v0.7.1` runs the Deploy workflow, which:

1. Runs the CI workflow on the tagged commit.
2. Builds the image once and publishes it as `ghcr.io/altoquepay/altoquepay-backend:0.7.1`.
3. Connects to the server with a key that can only run `deploy/deploy.sh`. The script takes the deploy files of that tag, pulls the image with the workflow's own short-lived token and restarts the API.
4. Checks that `/health` answers and `/openapi.json` reports the new version.

To deploy a published version again, for example to roll back, open the Deploy workflow in the Actions tab, choose **Run workflow** and type the version. The migrations are not undone, so roll back only to a version that works with the current database.

`docker compose logs api` on the server shows the API's output. Without an SMTP server, that output includes the password reset links.

#### Server setup

Done once per server:

1. Install Docker:

   ```bash
   sudo apt-get update && sudo apt-get install -y docker.io docker-compose-v2
   sudo usermod -aG docker ubuntu
   ```

2. Copy the `deploy` folder of a release from your machine. The server needs no access to the repository:

   ```bash
   git archive v0.8.0 deploy | ssh ubuntu@<server> 'mkdir -p altoquepay && tar -x -C altoquepay'
   ```

3. On the server, create `altoquepay/deploy/.env` from `deploy/.env.example` and fill it in.

4. Create a key pair used only by GitHub Actions, and add its public key to `~/.ssh/authorized_keys` on the server, limited to the deploy script:

   ```
   restrict,command="/home/ubuntu/altoquepay/deploy/deploy.sh" ssh-ed25519 AAAA... github-actions-deploy
   ```

5. In the repository settings, under Secrets and variables for Actions, add:
   - the secret `DEPLOY_SSH_KEY`, with that private key;
   - the variable `DEPLOY_HOST`, with the server's IP;
   - the variable `DEPLOY_KNOWN_HOSTS`, with the server's IP followed by the contents of its `/etc/ssh/ssh_host_ed25519_key.pub`, so the workflow only connects to that server.

6. Push the next release tag, or run the Deploy workflow with a version already published.

Without GitHub Actions, copy the whole release with `git archive <tag>` and build it on the server: `API_VERSION=local docker compose up -d --build`.

## Configuration

Settings are read from environment variables, or from a `.env` file in the directory where the command runs. The `.env` file must not be committed.

| Variable | Description | Default |
| --- | --- | --- |
| `DATABASE_URL` | SQLAlchemy URL of the database, using the `postgresql+asyncpg` driver | |
| `JWT_SECRET` | Secret that signs the JWTs, at least 32 bytes | |
| `JWT_EXPIRE_MINUTES` | Lifetime of a JWT, in minutes | `60` |
| `CORS_ORIGINS` | Comma-separated origins allowed by CORS | `http://localhost:4200` |
| `APP_TIMEZONE` | Time zone of business dates | `America/Lima` |
| `FIRST_ADMIN_EMAIL` | Email of the system administrator created at startup if missing; empty creates none | |
| `FIRST_ADMIN_PASSWORD` | Initial password of that administrator, who must change it on first sign-in | |
| `RESET_TOKEN_MINUTES` | Lifetime of a password reset link, in minutes | `30` |
| `SMTP_HOST` | SMTP server for password reset emails; empty logs the links instead | |
| `SMTP_PORT` | Port of the SMTP server, used with STARTTLS | `587` |
| `SMTP_USER` | SMTP user, also the sender of the emails | |
| `SMTP_PASSWORD` | SMTP password | |
| `FRONTEND_URL` | Base URL of the frontend, used to build the password reset links | `http://localhost:4200` |
